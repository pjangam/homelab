#### How it is running
Path taken: ZFS snapshots `@pre-v3` of both datasets and `rewrite_for_copies.sh` on the library (user, sudo), then 2.7.5 on the vectorchord postgres image, which migrated the DB off pgvecto.rs, then 3.3.1. `IMMICH_VERSION` is now an exact pin, never `release`. ML is capped at `cpus: 2`, and the load guard (`services/immich/load_guard.sh`, systemd --user `immich-load-guard`) stops the `immich_*` containers at >=93°C for 1 min, <1.5GB free memory for 1 min or >=95% CPU for 10 min, pushes to ntfy, and keeps them down until `load_guard.sh --reset`.

#### Could an old Intel MacBook Pro be the Immich server? (asked 2026-09-19)
Three shapes, cheapest first:
- **(1) Put 16GB in xero - still the best answer.** The blocker is one number: 8GB is not enough *with ML enabled*. The RAM is a removable SO-DIMM and confirmed expandable (see "Check if server RAM is expandable", Done: a 32GB stick went in on 2026-10-08), so a DDR4 2666MHz stick unparks this for a couple of thousand rupees, with nothing moved and no machine added. Everything below is a workaround for not doing this.
- **(2) Keep Immich on xero, move only the ML to the MacBook.** Immich supports [remote machine learning](https://docs.immich.app/guides/remote-machine-learning/): the ML container runs on another host and the server is pointed at it under Administration -> Settings -> Machine Learning. **Add** the remote URL rather than replacing the local one, so jobs fall back when the laptop is off, and keep both ends on the same Immich version or expect bugs. This targets the actual blocker - the ML model is what does not fit in 8GB - while photos, the database and the ZFS story stay exactly where they are. An i5/i7 will also chew through face detection far faster than the N5105.
- **(3) Move all of Immich onto the MacBook - the one to avoid.** It breaks the part of this setup that is actually good: the library lives on `datapool` with `copies=2`, `sync=always`, scrubs and rclone backups, and that history includes real recovered corruption. Serving it from a laptop SSD gives all that up, and serving it over NFS/SMB from xero adds a failure mode to every photo request. macOS itself is a poor 24/7 server (Docker Desktop is a VM with slow bind mounts, plus sleep, updates and login sessions), and installing Linux on an Intel Mac means Broadcom WiFi and fan control to sort out.

**The laptop is a 2019 16" MBP: i7-9750H (6c/12t, 2.6GHz), 16GB DDR4-2666, UHD 630 (given 2026-09-19).** That is roughly 4-6x xero's N5105 in multicore and twice its RAM, which sharpens the answer:
- **Remote ML needs no access to the photos at all.** The ML service receives images over HTTP from the server; only a model cache lives on its side. So Docker Desktop's slow bind mounts, the usual reason not to run things on macOS, simply do not apply here - it is one container, a cache volume and a port. No Linux install, and specifically no fight with a **T2 Mac**, which this is: T2 machines need patched kernels for the keyboard, audio and NVMe, so option (3) is worse on this hardware than on a generic Intel box.
- **The one-time import is where it pays.** Running ML over ~13k photos is the heavy job; incremental ML afterwards is minutes a week. Point Immich at the laptop for the initial pass, then let it fall back to xero.
- **It may unpark Immich for ₹0, for the import at least.** If ML is what does not fit in 8GB, moving ML off xero may be enough on its own - worth testing before buying the RAM stick, not instead of it. But the laptop is **rarely used and normally asleep** (confirmed 2026-09-19), so treat it as a machine borrowed for the one-time backlog pass, not a node Immich depends on: keep xero's local ML as the fallback, and let the RAM upgrade be what makes the steady state work.
- **Energy and heat are the real objections (raised 2026-09-19), and they only bite if it runs 24/7.**
  - **As a one-off import:** negligible. Sustained all-core load on that chassis pulls roughly 60-90W from the wall, so even 12 hours of it is under 1 kWh - about ₹5-8, once. Not a reason to avoid it.
  - **As an always-on server: don't.** Idle-with-lid-closed is ~10-15W *on top of* xero's ~12W, so it roughly doubles the always-on stack's share of the bill (~₹50-90/month against the ~₹130-175 measured in the power audit) for a machine that duplicates something already running.
  - **The heat is the more serious half.** The 2019 16" is a famously thermally-tight design; sustained ML sits the CPU near 100°C with the fans flat out, six-year-old thermal paste makes that worse, and continuous heat is exactly what ages a battery into swelling. A machine kept hot *and* permanently plugged in is the combination to avoid.
  - **Mitigations for the import:** cap Immich's ML job concurrency and give the container a CPU limit rather than letting it take all 12 threads, run it lid-open on a stand (not clamshell) in a cool part of the day, and keep it awake with `caffeinate` only for as long as the pass takes.
  - **Or skip the laptop entirely:** with 16GB in xero, the N5105 can grind the same backlog unattended over a day or two of background work. Slower, silent, no heat worry, and it is the machine that has to run the steady state anyway.
- **Battery age matters more than battery health here.** A 2019 cell in a machine left plugged in 24/7 is the swelling risk; check cycle count and condition before committing it to anything permanent.
- **Is this the same MacBook that runs the Claude sessions and the clawlight focus agent?** If so it is not a spare, and everything above is opportunistic - it works only while the laptop is awake and at home, which the fallback URL already covers.

**What to check on the laptop before either (2) or (3):** its RAM and CPU, its battery health (a swollen cell in a machine left plugged in 24/7 is a fire risk, and a healthy one is a free UPS - better than anything xero has), whether it can run lid-closed without sleeping, and its idle draw, which is likely 10-20W against xero's ~12W and runs on mains all day.
