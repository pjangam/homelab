# Offsite backup for Immich photo data
**Status:** Done

**Why:** Vaultwarden and HA config are already backed up daily to Dropbox via rclone. Immich's photo data (`datapool/immich-upload`, `datapool/immich-db`) has no copy off the Kingston SSD - the ZFS pool itself is a single disk (see above). Since 2026-10-22 it is the only copy of much of it: the Takeout zips and the phone-uploads copies were deleted once Immich had them, and the phone no longer has the May 2024 trip videos. Wider than Immich: nothing on `datapool` has a copy off xero.
**Outcome:** done 2026-10-26. Off-site copy running: `projects/immich-backup/archive_to_glacier.sh` puts every original Immich knows (both users and the birthday external library) plus the newest DB dump into GPG tar bundles in S3 Glacier Deep Archive (`pramod-immich-backup`, us-east-1). First full run 2026-10-23: 18,853 files, 80.5GB, 24 bundles. Cron repeats it at 04:00 on the 1st, and the healthcheck alerts after 33 days without a completed run. `recovered-media` (2 files) and `phone-uploads` are all in Immich, so the archive covers them; `documents` goes to Dropbox.
- Not pursued: the SD-card local copy. User, 2026-10-26: nice to have, not needed. A dead Kingston is restored from Deep Archive (12-48h, ~$0.20), or prevented by the "ZFS mirror" entry.
- Left for the user: delete the two probe objects under `immich/test/` from the S3 console (the upload-only key cannot).
- Not yet seen: the first incremental run (2026-11-01), which should pick up `GOPR0178.MP4` from 2026-10-26.

#### Approach
A naive rclone-to-Dropbox push doesn't actually make sense here: the whole point of self-hosting Immich is avoiding paying for cloud photo storage, so continuously syncing the full photo set to cloud storage undermines that. If pursued, needs a different shape - compress/archive first, and use a cold-storage tier (e.g. S3 Glacier / Glacier Deep Archive) priced for rarely-accessed disaster-recovery data rather than active-sync storage, not a Dropbox-style always-on sync.

#### Options (2026-10-18)
Two separate failures, two separate fixes:
- **A dead SSD:** the ZFS mirror entry (a second 1TB SSD, ~Rs 5-8k). Local, so it does not help with fire, theft or a pool lost to a crash.
- **Fire, theft, a lost pool:** an encrypted copy off the premises:
  - restic to Backblaze B2: ~$6/TB/month, so ~Rs 130/month for 250G. Encrypted on xero, incremental, nightly cron, easy partial restores. Recommended in conversation; the restic password could reuse `BACKUP_PASSPHRASE`.
  - restic to a Hetzner Storage Box: flat ~EUR 4/month for 1TB, over SSH. Similar value once it outgrows 500G.
  - S3 Glacier Deep Archive: ~Rs 25/month to keep, but ~Rs 2,000 and up to 12h to restore, 180-day minimum. Last-resort copy only; restic fits it poorly.
  - A disk at a relative's house: Pi + USB disk on Tailscale, restic or `zfs send`. No monthly cost, but another device to own and keep online.

The "Approach" note above says cloud undermines self-hosting; the counter-argument from 2026-10-18 is that a cold backup for a couple of hundred rupees a month is still far cheaper than Google One, and nothing day-to-day depends on it. The first upload is ~240G at Airtel's upstream: half a day to a few days.

#### Design (2026-10-22)
- **What:** Immich's `library/` (72G of originals) and the nightly DB dumps in `backups/` (~0.5G). Not `encoded-video/` (55G) or `thumbs/` (5.7G): Immich regenerates both from the originals. `albums` (6G) and `recovered-media` (0.9G) are small enough to ride along. `documents` already goes to Dropbox.
- **Local - SD card (1TB Samsung, interim):** in a USB 3 reader on xero (no built-in slot). `f3probe` it first (fake-capacity cards are common). Own single-disk ZFS pool, nightly incremental `zfs send` of `immich-upload` and `immich-db` snapshots, monthly scrub (cards fail without SMART warning). Replace later with a 2TB USB HDD (~Rs 6-7k) or the mirror SSD above; same scripts. Covers a dead Kingston, not fire/theft.
- **Off-site - S3 Glacier Deep Archive:** compression gains nothing (`compressratio` 1.01x: JPEG/HEIC/H.264 are already compressed), but bundling cuts ~18k files to a few dozen objects, which removes the per-object cost (~40KB billing overhead each, PUTs ~$0.05/1000). Monthly: the originals added since the last bundle -> one tar -> gpg (`BACKUP_PASSPHRASE`) -> one DEEP_ARCHIVE object; first run ~72G as ~5G bundles. Append-only (Immich never rewrites originals), which fits the 180-day minimum; deleted photos stay in the archive. Each upload carries the latest DB dump and the file -> bundle manifest. Key on xero is upload-only (no delete/overwrite). AISPL account (Indian address, INR billing), bucket in `us-east-1` (N. Virginia): half Mumbai's price and a continent away from Pune; restores take 12-48h either way. Moving region later means re-uploading everything, so it is set once.
- **Cost:** ~$0.99/TB/month in `us-east-1` (Mumbai ~Rs 0.16/GB, about twice that, per a reseller's list, 2026-10-22): storage ~Rs 6.5/month at 75G, ~Rs 8-10/month all in (PUTs <Rs 1, 18% GST on AISPL bills), ~Rs 15-20 after a year of growth (2-5G/month new photos + a 0.5G DB dump kept monthly). The first month is a little more (the 72G upload). Versus the Rs 150/month Google One plan on the user's wife's account (live photo service, not a like-for-like swap: dropping it means her Takeout into Immich first). Full restore of 75G: ~48h (bulk), ~$0.20 retrieval, egress inside the 100GB/month free tier. (The ~Rs 2,000 restore estimate above was for all 240G of `datapool`, mostly egress.) Compared 2026-10-22: B2 ~Rs 35/month, Google One 100GB ~Rs 130.

#### AWS setup (user, before the scripts)
1. New AWS account (the old one was suspended for inactivity). With an Indian address it is AISPL: INR billing, Indian card; it can still use `us-east-1`, where the bucket goes.
2. MFA on the root login; root is for the console only.
3. Billing -> Budgets: a $1/month budget with an email alert.
4. Then the session: create the bucket and an IAM user whose key can only `s3:PutObject` (no delete, no overwrite of existing keys), key into `.env` as `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`.
