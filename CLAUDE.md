# Working in this repo

- Write shell/diagnostic scripts into this repo (in the owning project's folder, see below), not `/tmp` or a scratchpad - even for one-off or throwaway-feeling scripts. Unnecessary files in the repo can always be cleaned up later; anything left only in `/tmp` is gone once the session/machine cycles, and the work it did goes untracked. Delete it from the repo afterward if it turns out not to be needed, rather than never having committed it.
- **Work on `main`. Do not create branches.** Commit straight to `main` and push when the work is done. This is a single-maintainer homelab repo where everything lands on `main` anyway, and more than one Claude session often has this same working tree checked out at once - a branch created in one session silently swaps the checkout under the other. That is not hypothetical: on 2026-09-11 a session branched by habit, a second session's commit landed on that branch instead of `main`, and untangling it needed a rebase to drop the duplicates once the other session had recreated its work on `main`.
- **Put a new file where its purpose says, not its file type.** The root was split into four homes on 2026-09-15. Still to move, deferred to a later session: the projects that deploy to the wol-sender Pi or the Mac - `clawlight/`, `scripts/` (clawlight, pi-buttons, wol-sender), `systemd/`, `esp32/` and the root `*_buttons_setup.md` files. Leave them in place until that session (the user starts it); until then new files for those projects go next to their existing ones. The Mac gets clawlight's files from a git clone (settled 2026-09-16), and its hooks and launchd plist hold the clone's `clawlight/` path, so moving that folder means re-running `setup-mac-focus-agent.sh` on the Mac from its new location. Everything else follows:
  - `projects/<name>/` - code this repo builds, with everything that belongs to it: its scripts, tests, cron job, systemd units and setup doc. One folder per project that has code; its `tracker/<slug>.md` links to it with the same name.
  - `services/<name>/` - config for off-the-shelf software we only run (Caddy, Mosquitto, ntfy, Tailscale sidecars).
  - `tools/` - helpers used by more than one project (notify, network diagnosis, ESP32 flashing, repo tooling).
  - `docs/` - reference and incident write-ups not owned by one project.
  - `tracker/` - one `<slug>.md` per project of every status, its plan, research, budget and Log (since 2026-11-18; `tracker/README.md`).

  Docker's live data directories (`vw-data/`, `HOMEASSISTANT_CONFIG/`, `etc-pihole/`, `postgres/`, `library/`, `certs/`, `backups/`) stay at the root on purpose. Before moving anything, read `tools/repo-tools/README.md`: check who calls it by path from outside git (the crontab, installed systemd unit copies, compose bind mounts, the Pi's and Mac's deploy scripts) and recreate or re-deploy what the move touches.
- **A folder is not a home until its `README.md` says what it is.** Every folder under `projects/`, `services/`, `tools/` - and the deferred `scripts/<name>/`, `esp32/<name>/` - has one. Deliberately **not** a "before Done" rule like the two below: the README arrives with the folder's **first file**, because a half-built project is exactly when "what is this, what runs it, what breaks it" is hardest to reconstruct, and the folder outlives whoever remembered. Keep it current in the same work, the way the checklist is. What it has to answer: what the thing is and why it exists, which host it runs on, what starts it (container, `systemd --user` unit, cron line), where its state and secrets live, what to re-run after a change, and the traps that cost someone a day - with a table of the folder's scripts when there are more than two or three. Not a changelog: the story goes in the project's `tracker/` file, the incident in `docs/incidents/`, and the README links to them. The same commit also adds the folder's line to the root `Readme.md` index (its `projects/`, `services/` or `tools/` table): a folder missing from the index is as hard to find as one without a README, which is how `projects/smart-switch` went unlisted on 2026-11-05. `tools/repo-tools/check_readmes.sh` lists every folder missing a README or an index line; `.githooks/pre-commit` runs it `--staged`, so a commit that creates a folder without either is stopped (it cannot fail on the repo's existing state). The root `Readme.md` is **host-level only** - bringing xero up, OS and hardware quirks, plus the index of the folders above. Per-project prose does not belong in it; that was the clause the 2026-09-15 split left undone until 2026-11-04.
- **Hardware work is not done until `docs/hardware.md` says so.** If a change adds, replaces, re-addresses or retires a device (a board, a Pi, a sensor, a new static IP), or changes what runs on one (container, systemd unit, cron job, firmware version, GPIO pins), update that device's entry as part of the same work, before setting the project's `tracker/` Status to Done. The file is **gitignored** because it gathers LAN addresses and service locations into one lookup, so `git status` will never show it going stale. That is how the WLED aarti-lights ESP32 went unlisted for three days after it shipped. Run `tools/repo-tools/check_hardware_md.sh` before closing the work: it lists what is running on xero and the Pi, and every LAN address the docs mention, that the file does not. Never commit the file.
- **A device added to Home Assistant is not done until it is on the Home dashboard, in its room** (user, 2026-11-06). Same shape as the two rules around it: on 2026-11-05 the kandil switch sat in HA under its bench name with no tile, and the Diwali WLED board was never added at all, so neither showed up where the user looks.
  - **Ask the user which room** it goes in. Never guess from the device or project name.
  - **In HA:** give the entity a plain name (what the user calls it, not the firmware or bench name), an icon if the default is wrong, and set the device's area to that room. The entity_id can stay; automations use it.
  - **On the dashboard:** add a tile to that room's view in `projects/ha-dashboard/dashboards/home.yaml`, push it with `ui_dashboard.py restore`, and check it with `shot_dashboard.sh` (it fails on error cards). Look at the screenshot. Commit `home.yaml`.
  - **Record it:** the device's `docs/hardware.md` entry says its HA name, area and tile.
  - Applies to anything the user operates or reads: switches, lights, sensors worth seeing. Diagnostic-only entities (uptime, WiFi signal) need the name and area, not a tile.
- **A project that serves anything is not done until `projects/endpoints/endpoints.toml` lists it.** Same shape as the hardware rule above, and for the same reason: the endpoint index at `https://xero.<tailnet>/endpoints/` is rendered from that one file, so a service that arrives, moves port or retires without it being edited leaves the page quietly wrong - which is precisely the "what is running here and where do I open it" problem the page exists to solve. It covers more than web pages: a new MQTT topic, a DNS or SMB change, a new UDP feed and a new tailnet name all belong on it. Add the entry as part of the same work, before setting the project's `tracker/` Status to Done, then re-render on xero with `projects/endpoints/render_endpoints.py`. Run `tools/repo-tools/check_endpoints_toml.sh` before closing the work: it lists every host port `docker-compose.yml` publishes and every path the Caddyfile handles that the file does not mention. It reads the tracked config, not the live machines, so it cannot see the systemd --user services, the Pi or the ESP32 - if the work added one of those, check by hand. Never put credentials or the tailnet suffix in it; write `{tailnet}` and let the renderer substitute. The rendered `site/` is gitignored and must not be committed or hand-edited.
- **Write docs as tables and bullets, not paragraphs** (user, 2026-11-05). Applies to `tracker/` files, READMEs, `docs/` and bench guides - anything the user scans later on GitHub or the projects dashboard.
  - **Tables** for anything with columns: costs and parts (part / price / have it?), option comparisons, connections (from / to / why), hosts and ports.
  - **Bullets** for lists of facts, steps (numbered when order matters), traps and decisions. One idea per bullet, led by a bold label when that helps scanning.
  - **Paragraphs** only for the short "why" or a story that needs its sequence, a few sentences at most.
  - When adding to an entry that is already a wall of text, put the new material in this shape (its own `####` subsection if it is a table) rather than extending the paragraph.
  - **Parts to buy are a fenced ` ```parts ` block, never a markdown table** (user, 2026-11-14). The projects dashboard's "Add to shopping list" button reads only those blocks (`projects/projects-ui/src/lib/parts.js`): one row per part, `qty | item | est | note`, and a `# Option name` line starts a group of alternatives so one option can be added without the other. See the "Workbench stock" entry for an example.
- **Hand new ideas and wiring to the repo's agents** (`.claude/agents/`, user, 2026-11-14), rather than writing the entry or diagram inline:
  - **`idea-dump`** - any new `tracker/` file for an idea the user wants recorded, not built now. It researches, budgets it (Cost and Effort), prices parts in a ` ```parts ` block, writes the Open items checklist, regenerates the index and commits. Pass it the idea in the user's words plus everything decided in the conversation.
  - **`circuit-diagram`** - wiring diagrams and bench guides for hardware builds.
  - **`architecture-review`** - an independent, read-only review of a plan, design or built system (user, 2026-11-15). Run it before building a plan and after building something non-trivial. Pass only the target and the user's constraints, **not your own findings**, so the review is not anchored on yours; then go through its findings with the user before applying any.
  - Small edits to an existing tracker file (a decision, a log line, a status change) stay inline.
  - **Enforced for new ideas:** `.claude/settings.json` runs `tools/repo-tools/require_idea_dump.py` before every Edit/Write/Bash; a new Backlog/Parked file in `tracker/` written outside `idea-dump` is denied with a message to delegate. New Active/Done files for work done in the session are not affected.
- **Projects live one per file in `tracker/<slug>.md`** (since 2026-11-18; format and rules in `tracker/README.md`). Check the project's file for context before starting work, and update it when its state changes. Status, priority and budget are the `**Status:**` / `**Priority:**` / `**Cost:**` / `**Effort:**` lines under its `# Title`: change the line, never move or rename the file. Every open project carries a rough budget - Cost in rupees and Effort in evenings or weekends; the commit hook rejects an open file the commit changes without one. `PROJECTS.md` is now a **generated index** - never edit it by hand: after changing tracker files run `tools/repo-tools/tracker.py index` and commit `PROJECTS.md` with them (`git commit -- tracker/<slug>.md PROJECTS.md`); the hook only checks it matches. On a `PROJECTS.md` merge conflict, regenerate rather than merge.
- **Every project you touch leads with its `#### Open items` checklist, kept current in the same work.** Straight under the header lines, one short line per item, each led by its owner: `- [ ] **Pramod:** ...`, `- [ ] **Together, <when>:** ...`, `- [ ] **Claude:** ...`. Before you finish, the checklist must match what is actually left: delete what got done (and Log it), add what the work turned up - including what the user said they will do themselves, and anything agreed for a later session with a time. The user reads the dashboard's open-items panel (`projects-ui`, `https://xero.<tailnet>/projects`) to see at a glance what is waiting on whom, so an item left out there is effectively forgotten. Enforced at commit time: `.githooks/pre-commit` runs `tools/repo-tools/fix_open_items.sh`, which checks the tracker files the commit changes (`check_open_items.sh --staged`) and fixes what breaks the format - a misplaced checklist mechanically, an old Next step, an ownerless item or a missing checklist by a headless `claude -p` (Read/Edit on those files only). In a normal commit it re-stages the fix; in a `git commit -- <paths>` it fixes the working tree and stops, so run the same commit again. Read what it printed and check its conversion - it guesses owners - but writing the file properly yourself is better than leaving it to the hook.
